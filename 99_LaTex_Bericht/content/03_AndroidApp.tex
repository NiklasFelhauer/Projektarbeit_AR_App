\section{Android App}
Die App verbindet die Brauanlage im Automatisierungstechnik-Labor mit dem Smartphone. Sie zeigt Live-Messdaten (z.B. Tanktemperaturen, Ventil-/Pumpenzustände), die per MQTT von einer SPS empfangen werden. Außerdem erkennt sie die drei großen Brauanlagen-Tanks über die Kamera (Objekterkennung) und bietet individuelle Einstellmöglichkeiten. Technisch nutzt die App eine Single-Acitiviy-Architektur, das bedeutet, es gibt eine einzige Hauptseite (MainActivity), die mehrere Bildschirme (Fragmente) beinhaltet, zwischen denen per Tab-Leiste gewechselt werden kann. Ein MainViewModel hält Daten und Einstellungen zentral, damit die Daten beim Tab-Wechsel erhalten bleiben. Änderungen werden über LiveData automatisch in allen Tabs sichtbar und stetig aktualisiert.


\subsection{MainViewModel}

Das \verb|MainViewModel| bildet die zentrale Datenschnittstelle der App. 
Es handelt sich um eine Android-Komponente, die Daten unabhängig vom User Interface (UI) im Hintergrund verwaltet.
Das ist notwendig, weil die einzelnen Tabs beim Wechseln neu geladen werden und lokale Variablen verloren gehen würden.
Das ViewModel speichert die Werte zentral und stellt sie allen Tabs zur Verfügung.

Im \verb|MainViewModel| wird außerdem die MQTT-Verbindung aufgebaut und alle eingehenden Nachrichten verarbeitet. 
Die Sensordaten werden dabei im JSON-Format übertragen, zum Beispiel:
\lstinline|{"tank_1": 65.5, "tank_2":70.2, "tank_3": 23.4, ...}|

Beim Eintreffen einer Nachricht wird diese in eine Datenstruktur umgewandelt (geparsed) und den Tabs bereitgestellt:

\begin{lstlisting}[language=Kotlin]
override fun messageArrived(topic: String?, message: MqttMessage?) {
    val raw = message?.toString() ?: return
    val obj = JSONObject(raw)
    val parsed = mutableMapOf<String, Float>()
    obj.keys().forEach { key ->
        parsed[key] = obj.getDouble(key).toFloat()
    }
    _allValues.postValue(parsed)
}
\end{lstlisting}

Die App verfügt über die folgenden zwei Datensammlungen:
\begin{itemize}
    \item \verb|_tankTemperatures|: enthält die Temperaturwerte der Tanks
    \item \verb|_allValues|: enthält alle Werte aus der MQTT-Nachricht 
\end{itemize}
Beide Variablen sind vom Typ \verb|LiveData|. 
Das bedeutet, dass sie automatisch alle Bildschirme aktualisieren, sobald sich der Wert ändert.
Dadurch werden Temperaturänderungen oder Schaltzustände der Brauanlage in Echtzeit in der App sichtbar.
\\Der grundsätzliche Ablauf vom \verb|MainViewModel| ist vereinfacht in \autoref{fig:DatenflussMainViewModel} dargestellt. Die Daten werden vom MQTT-Broker an das Smartphone weitergeleitet, dort im \verb|MainViewModel| empfangen und anschließend an die unterschiedlichen Tabs weitergeleitet.

\subsection{Navigation}
Die App ist nach der Single-Acitivity-Architektur aufgebaut. Die \verb|MainActivity| enthält ein \verb|NavHostFragment|, das die einzelnen Tabs (Fragmente) rendert. Die Tab-Leiste ist als \verb|Top Navigation| umgesetzt und wird per \verb|setupWithNavController(...)| direkt mit dem \verb|NavController| verbunden. Dadurch übernimmt die Navigation-Komponente das Umschalten zwischen Tabs automatisch (inklusive korrekter Titel-/Backstack-Verwaltung).
Ein erneutes Antippen des bereits aktiven Tabs wird bewusst ignoriert, um unnötige Re-Loads zu vermeiden. Der Zurück-Button (\texttt{onBackPressed}) beendet die App.

\subsubsection{Kamera-Tab}
Der Kamera-Tab wird standardgemäß als erstes beim Starten der App geöffnet und nutzt die CameraX-API, um den Kamera-Livestream des Smartphones anzuzeigen. Jedes Frame (einzelnes Bild) wird an die \verb|ObjectDetectorHelper|-Klasse geschickt, welche das benutzerdefinierte Tensorflow-Lite Modell \verb|Tanks_V2.tflite| nutzt, um Tanks der Brauanlage zu erkennen und die Koordinaten der zugehörigen Bounding-Boxen zu berechnen.
In der \verb|OverlayView|-Klasse wird der Tank-Name, Erkennungssicherheit des Modells (Score) und die aktuelle Temperatur als Overlay auf einem erkannten Tank angezeigt. Die Temperaturdaten kommen regelmäßig per MQTT direkt von den Temperatur-Sensoren der Brauanlage im JSON-Format, zum Beispiel als:
\lstinline|{"tank_1": 65.5, "tank_2":70.2, "tank_3": 23.4, ...}|
Diese Daten werden im MainViewModel verarbeitet.

In der \verb|CameraFragment|-Klasse werden die Temperatur-Daten aus dem MainViewModel kontinuierlich beobachtet. 



\subsubsection{Overview-Tab}

Die Symbole der Sensoren und Aktoren ändern ihre Farbe basierend auf dem Zustand, der per MQTT übermittelten Schaltzustände. Initialisiert wird der Status in der App mit dem float-Wert 3f.  
Es gilt folgende Farbzuweisung, die auch in \Cref{lst:ventil} zu sehen ist.
\begin{itemize}
    \item \textbf{0}: aus/geschlossen $\rightarrow$ rotes Icon
    \item \textbf{1}: an/geöffnet $\rightarrow$ grünes Icon
    \item \textbf{sonst}: Startwert/unbekannt $\rightarrow$ graues Icon  
\end{itemize}

\begin{lstlisting}[language=Kotlin, caption={Zustand von \texttt{ventil1} setzen}, label={lst:ventil}]
    val ventil1State = values["ventil_1"] ?: 3f
            when (ventil1State){
                0f -> binding.ventil1.setImageResource(R.drawable.vlv1_red)
                1f -> binding.ventil1.setImageResource(R.drawable.vlv1_green)
                else -> binding.ventil1.setImageResource(R.drawable.vlv1_gray)
            }
\end{lstlisting}

\subsubsection{MQTT-Tab}
Dieser Tab dient dazu, die MQTT-Verbindung zu überprüfen und gegebenenfalls die Verbindung zum Broker neu aufzubauen.
Dafür gibt es einen \glqq Verbinden \grqq -Button, der die Funktion \verb|ViewModel.startMqtt()| aufruft.
Das \verb|MainViewModel| stellt die rohen MQTT-Daten im JSON-Format zur Verfügung. 


\subsubsection{Settings-Tab}
Im Settings-Tab kann das Objekterkennungsmodell des Camera-Tabs noch detaillierter eingestellt werden. Es können die ML-Paramter wie \verb|Treshold|, \verb|MaxResults|, \verb|Delegate| und \verb|Model| manuell angepasst werden. Diese werden direkt ins \verb|MainViewModel| geschrieben.
\begin{enumerate}
    \item \textbf{Threshold}: Die minimal Erkennungssicherheit des Modells, um ein Objekt zu klassifizieren. Default: 0,8 bzw. 80 \%
    \item \textbf{MaxResults}: Anzahl der gleichzeitig erkannten Objekte. Default: 3
    \item \textbf{Delegate}: Auswahl, ob die Objekterkennung auf der CPU oder GPU läuft. Die GPU bietet eine höhere Verarbeitungsgeschwindigkeit, jedoch ist diese bei alten Smartphones nicht vorhanden. Default: CPU
    \item \textbf{Modell}: Auswahl des Objekterkennungsmodells, es gibt das Standardmodell EfficientDetLite2 und das benutzerdefinierte Brauanlagen-Modell. Default: Brauanlage
\end{enumerate}


\subsubsection{Promillerechner-Tab}
Durch Arbeiten an der Brauanlage ist es nicht auszuschließen, dass auch das ein oder andere Bier getrunken wird. Um im Anschluss die Verkehrstüchtigkeit zu gewährleisten, ist in der App ein Promillerechner integriert. Hierbei kann durch Klicken auf den \glqq Bier-Button \grqq die Anzahl der getrunkenen Biere ausgewählt werden. Anschließend wird basierend auf dem Körpergewicht die Zeit berechnet, um wieder nüchtern zu werden. Die Anzahl der Biere kann durch einen langen Klick wieder auf 0 zurückgesetzt werden. 

\noindent 
Wie in \autoref{eq:modell} gezeigt, ergibt sich die maximale Zeit, um wieder nüchtern zu sein aus der Blutalkoholkonzentration (BAC) und der Abbaurate des menschlichen Körpers.

\begin{equation}\label{eq:modell}
\begin{aligned}
\mathrm{BAC} &= \frac{12\,n}{0,68\,m},\\
t &= \max\!\left\{0,\ \frac{\mathrm{BAC}}{0,1}\right\}
   = \max\!\left\{0,\ \frac{12\,n}{0,68\,m \cdot 0,1}\right\}.
\end{aligned}
\end{equation}

\noindent\textbf{Mit folgenden Zusammenhängen:}
\begin{description}
  \item[$\mathrm{BAC}$] Blutalkoholkonzentration in Promille (‰)
  \item[$n$] Anzahl der getrunkenen Biere, es wird pro Bier \(\approx 12\,\mathrm{g}\) reiner Alkohol angenommen
  \item[$m$] Körpergewicht in Kilogramm
  \item[$t$] maximale Zeit bis der Alkohol vollständig abgebaut ist
\end{description}

\noindent\textit{Hinweis:} Es handelt sich um eine vereinfachte Abschätzung (kein medizinisches Gutachten). Individuelle Faktoren
(z.\,B. Trinkverlauf, Geschlecht, Magenfüllung, tatsächlicher Alkoholgehalt jedes Bieres) bleiben unberücksichtigt.
